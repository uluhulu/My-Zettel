Изначально веб представлял из себя обычные html документы, благодоря которым заинтересованные люди могли обмениваться инофрмацией. Работало это все поверх http протокола. Это прикладной уровень модели tcp/ip или osi. При этом каждая доступная страница обладает своим адресом, а связь достигается за счет гиперссылок, которые позволяют из одной страницы перейти в другую. 

Изначально веб паутина - обмен документами, связанными гиперссылками.

Одного html стало мало, захотелось добавлять визуальную состовляющую и тогда появился css. Каскадные таблицы стилей, с помощью которых мы можем оформлять страницы. 

Сбор и отправление информации предполагают ее хранение. Здесь мы подходим к бэкенд технологиям, серверным технологиям, которые работают с данными.

Изначально, сама html страница не висит в воздухе. ПОсле того, как пользователь ввел адресс приложения, нажал enter в браузере, у нас отправляется http get запрос на сервер. Это может быть как простой веб сервер так и более сложный. Сервер в свою очередь знает какую html-ку по этому адресу отдать и он ее просто отправляет пользователю. После этого пользователь видет эту html отрисованную в браузере. 

Для того что бы отдавать статичные страницы, в которых нет динамических данных, достаточно иметь простейший веб сервер, который умеет отдавать статические данные. То есть, он слушает запросы и по этим запросам идентифицирует файлы, которые необходимо отдать. 

Если мы хотим собирать динамические данные хранить и отдавать их пользователю. Тут мы подходим к концепции баз данных. Сервер может как сохранять какие то данные, так и читать с нее. То есть мы какие то данные сохранили, сервер новые данные с базы данных вычитал, создал html с этими динамическими данными и вернул ее пользователю. 

Здесь происходит разделение - мы выделяем отдельно клиентскую и серверную часть, которую пользователь видит в браузере. 

По мимо html и css у нас появляется java script - язык программирования, который позволяет на страницу добавить какую то динамику. Открытие модальных окон, сложные анимации, обработку форм, валидацию и многое другое. По мимо этого java script позволяет добавить такую важную концепцию как асинхронные запросы. С помощью java script мы отправляем асинхронный запрос и в этот момент браузер у нас ждет ответа от сервера. Но страница при этом не обновляется. Мы просто находимся в режиме ожидания, но обновления страницы не происходит. Сервер возвращает уже не html. Он возвращает либо json либо xml или любой другой тип данных. Он возвращает нам данные, которы мы запросили. Json просто один из самых популярных типов данных. 
Мы просто берем данные из сервера и в нужных местах подставляем их на страницу. Делаем это исключительно за счет java script.Начиная с запроса, заканчивая подстановкой данных в нужные места.  Если раньше у нас было много html страниц, то сейчас у нас становится много java scripta, в котором вся эта логика по взаимодействию скрипта.

Как только мы вводим понятие асинхронных запросов и обработку всех этих запросов в java scripte, у нас происходит явное разделение frontenda  и backenda. Теперь это два отдельных приложения.

С появлением асинхронных запросов поняли что в большом количестве html нет смысла, потому что весь контент на странице мы можем подменять за счет java script скрипта и данных, которые присылает нам сервер, в формате json. Подобные приложения, которые содержат одну HTML страницу, называются spa - single page application. Приложения с одной страницей. Например мы эту страницу открыли, подгрузили данные о пользователе, потом мы ткнули на другую ссылочку, отправили на сервер асинхронный запрос и увидели страницу с информацией о платежной системе. В рамках одной страницы мы просто подменили данные, которые вернулись к нам с сервера. Возникает вопрос откуда мы получаем первичную html страницу ? Если фронтенд и бекенд это 2 отдельных приложения. Бэкенд это приложение которое взаимодействует с базой данных и возвращает какие то данные, а клиент это то, с чем мы взаимодействуем в браузере. Ведь мы упоминали что нужен сервер, который отдает html на гет запрос.Будет достаточно простейшего веб сервера (nginx, apache). 
Логика здесь такая : пользователь вводит url, http get запрос отправляется на сервер, этот сервер умеет отдавать статические файлы, и он отправляет html, css, js и картинки в браузер пользователя. Таким образом, frontend является полноценным отдельным приложением и за раздачу статики отвечает веб сервер.  А наш реальный backend, application server, в котором находится ядро приложения, бизнес логика, взаимодействие с базой данных, это отдельное приложение. Причем одним таким бэкендом может пользоваться много клиентов.Это может быть мобильное приложение, веб приложение, партнеры, взаимодействующие по апи. Работаем мы с этим сервером в формате вопрос ответ. 
На текущем этапе развитии этой системы фронтенд и бекэнд достаточно сложные и обособленные друг от друга приложения. 
На фронтенде, как мы уже выяснили, у нас много css, много java script, файлы других расширений : png, jpeg и т.д. Обрабатывать все это руками достаточно затруднительно. Поэтому нам на помощь приходят сборщики, такие как webpack, vite, rollup. Перед тем как сказать, какие файлы раздавать мы пропускаем наш код через этот сборщик. Сборщик подготавливает это все в удобном виде к продакшену. Сжимает файлы с помощью бейбл может подготовить код к работе в старых браузерах. По итогу мы пропускаем наши файлы через сборщик, получаем бандл - весь код нашего приложения. Этот бандл уже раздается веб сервером. А взаимодействие с бэкендом происходит в формате запрос ответ. Непосредственно на самом фронтенде. 
Инфраструктура бэкенда тоже усложняется и в текущий момент у нас есть ядро приложения, в этом ядре у нас описана бизнес логика. И есть база данных, с которой это ядро взаимодействует. База данных как правило изначально какая то реляционная (mySQL, postgres). Такая база данных представляет из себя набор связаных таблиц, где данные строго структурированы. Для определенного вида данных нас это устраивает, но в какой то момент мы хотим хранить хаотичные, слабо структурированные данные в виде документов. Одна из разновидностей noSQL баз данных это документо ориентированные базы данных.  Самая часто используемая это MongoDB. По мимо классического хранения данных нам так же может понадобиться быстрый доступ к каким то данным в виде кеша.
